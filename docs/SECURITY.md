# LOG3 Vault — ключі, секрети, мережа, межі доступу й приватність метаданих

## 1. Ключі

```
парольна фраза ──scrypt(сіль, n=2^15, r=8, p=1)──► майстер-ключ ──HKDF "kek"──► KEK
KEK загортає (AES-256-GCM, AAD = призначення) ключі даних і ключ ідентифікаторів  (config.json → crypto.keyring)
ключ даних  (key_id у заголовку кожного об'єкта) ── AES-256-GCM блоків і маніфестів
ключ ідентифікаторів ── object_id / content_id (HMAC-SHA256); ротацією не змінюється (дедуплікація)
ключ службових файлів = HKDF(ключ ідентифікаторів, "meta") ── HMAC repo-config.json і покажчиків версій
```

| Дія | Команда | Що відбувається |
| :-- | :-- | :-- |
| безпечне налаштування | `log3-vault init` | фраза лише зі змінної `LOG3_VAULT_PASSPHRASE` або файла `LOG3_VAULT_PASSPHRASE_FILE` (POSIX: файл не може бути доступним групі чи іншим, інакше `E_KEY_PERMS`), інтерактивно — лише зі справжньої консолі; не з аргументів CLI; мінімум 12 символів |
| ротація | `log3-vault key rotate` | новий випадковий ключ даних стає активним; попередні лишаються для читання старих версій |
| зміна фрази | `LOG3_VAULT_NEW_PASSPHRASE=… log3-vault key passphrase` | ключі перезагортаються під нову фразу; об'єкти не перешифровуються; стара фраза перестає відкривати локальну конфігурацію одразу, а backend-и — після розсилки підписаної конфігурації (робиться автоматично, `key publish` — повторно) |
| аварійний експорт | `LOG3_VAULT_EXPORT_PASSPHRASE=… log3-vault key export --out F` | усі ключі під окремою фразою; файл створюється з правами 0600 (у Windows — права каталогу); зберігати офлайн окремо від копій |
| стан | `log3-vault key status` | ключі, об'єктів на кожному, частка бюджету nonce; без секретів |

**Nonce.** AES-GCM із випадковим 96-бітним nonce на кожен об'єкт. Монотонний лічильник `sealed:<key_id>`
у каталозі й межа `crypto.max_objects_per_key = 2^30` (≪ 2^32, межа NIST SP 800-38D для випадкових nonce)
вмикають автоматичну ротацію перед backup. Межа: захоплення, перерване аварією до фіксації лічильника, не
врахує вже використані nonce (≤ кількості блоків однієї версії) — запас між 2^30 і 2^32 це покриває.

**Автентичність метаданих.** Об'єкти автентифікуються AES-GCM з AAD (заголовок + `object_id`), маніфест —
так само плюс перевірка `version_id`. Службові файли backend-а (`repo-config.json`, `version-*.json`)
підписані HMAC із прив'язкою до назви файла: `recover` відхиляє змінену політику (`E_META`, код 7) і
переставлені покажчики (`rejected_meta`). Параметри KDF із недовіреного файла обмежено (`n ≤ 2^20`,
`r ≤ 16`, `p ≤ 4`) ще до виведення ключа. Непідписані файли сховищ етапів 1–2 — лише з
`--accept-legacy-meta`, після чого слід виконати `key publish`.

**Журнали.** Секрети не потрапляють у вивід CLI, події каталогу, журнал навчання, журнал вузла (рядок
запиту й назва токена, без заголовків) і журнал модуля захисту (фрази й токени замінюються на `***`).

## 2. Мережевий режим (вузол)

| Вимога | Як забезпечено | Межа |
| :-- | :-- | :-- |
| перевірка сторони з'єднання | клієнт перевіряє сертифікат вузла за закріпленим `ca_file` і ім'я хоста; TLS ≥ 1.2 | клієнта вузол перевіряє токеном, а не сертифікатом (mTLS не реалізовано) |
| автентифікація | Bearer-токен; у `--tokens-file` лише SHA-256 токенів, порівняння за сталий час | токен передається в кожному запиті всередині TLS |
| права | ролі `reader` (читання, stat, info), `writer` (+ PUT об'єктів і службових файлів), `admin` (+ DELETE); дія поза роллю — 403 | `writer` не може видаляти, але може записати під тим самим `oid` інші байти (так repair замінює пошкоджену копію); клієнт це виявляє `verify` |
| відкликання | `log3-vault node-token revoke NAME`; файл перечитується за mtime — діє з наступного запиту без перезапуску | старі з'єднання завершують поточний запит |
| ліміти | розмір об'єкта (`--max-object-mib`, 413), службового файла (1 МіБ), обов'язковий Content-Length (411), квота (507), одночасні з'єднання (`--max-connections`), блокування IP після 10 невдалих автентифікацій за 60 с (429) | захист від DoS базовий: однопроцесний сервер без черги запитів |

Перевіряє `tests/test_vault_stage3.py::test_node_roles_revocation_and_limits`. Без `--tokens-file` вузол
приймає один токен зі змінної `LOG3_NODE_TOKEN` як `admin` (сумісність етапу 1).

## 3. Межі доступу локального CLI (ОС)

Локальний CLI **не має ролей**: будь-хто, хто може читати каталог сховища, бачить метадані, а хто знає
парольну фразу — дані. Межа — права ОС:

- `init` (і `recover`) створює каталог сховища з доступом лише для власника: POSIX `0700`; Windows —
  ACL без успадкування для власника, SYSTEM і Адміністраторів (SID, тож працює в локалізованих системах).
- `doctor` показує, чи має доступ хтось інший (`repo_access_owner_only`).
- Служба `run` працює без парольної фрази: вона бачить лише зашифровані об'єкти й метадані каталогу.
- Адміністратор ОС і процеси від імені власника мають повний доступ — від них сховище не захищає.

## 4. Приватність метаданих

| Де | Що видно | Чого не видно |
| :-- | :-- | :-- |
| вузол / backend-каталог | кількість, розміри й час запису об'єктів; `object_id` (ключований HMAC — без ключа не перевірити здогадку про вміст); `repo-config.json` (KDF, сіль, загорнуті ключі, політика, назви й адреси backend-ів); покажчики версій (`version_id`, час створення, `oid` маніфесту) | імена файлів, шляхи, джерела, розміри окремих файлів, вміст — усе це лише в зашифрованих маніфестах і блоках |
| локальний каталог `catalog.sqlite` | шляхи файлів (таблиця `files` для `file_id` між версіями), корінь джерела й назва набору, час і стани версій, події | вміст файлів |
| журнал навчання `<repo>/learn/` | клас типу файла за розширенням, розміри, ентропія, рішення кодека, псевдонім лінії файла `sha256(repo_id:file_id)` | шляхів і імен файлів |
| метрики Prometheus | агрегати; мітки — лише стан версії, стан завдання, назва backend-а з конфігурації | шляхів, id файлів і версій, секретів |

**Де розшифровуються маніфести і де працює пошук.** Лише на клієнті, у пам'яті процесу CLI. `find` без
`--path` фільтрує версії за каталогом (версія, джерело, назва, стан, час) без парольної фрази;
`find --path GLOB` розшифровує маніфести відібраних версій локально. Повнотекстового пошуку вмісту нема:
він необов'язковий і не впливає на збереження довільних файлів — будь-які байти зберігаються однаково.
