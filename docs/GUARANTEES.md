# LOG3 Vault — перевірювані гарантії (етап 3)

Кожне твердження нижче має місце в коді, яке його забезпечує, і перевірку, яка його відтворює. Перевірки
запускаються в нових процесах і читають стан із диска: `python -m log3.defense --stage matrix --profile full`
(матриця відмов), `python -m pytest tests/test_vault_*.py` (тести). Результати прогону на конкретному
комп'ютері — [results/vault/failure_matrix.md](../results/vault/failure_matrix.md).

**Межі перевірки.** Аварії — це `os._exit` у названих точках коду (`LOG3_VAULT_CRASHPOINT`), а не
вимкнення живлення. Вузол — окремий процес на тому самому диску, тому «відмова вузла» тут означає
процесну або мережеву відмову, а не втрату незалежного фізичного диска. Втрату живлення фізично не
перевіряли: гарантія для неї спирається на те, що ОС і носій чесно виконують `fsync`.

## 1. Що означає кожен рівень

| Рівень (`protection_level`) | Що вже правда | Що ще НЕ правда | Де в коді |
| :-- | :-- | :-- | :-- |
| `accepted_local` — локальне приймання | Блоки й маніфест записано в spool через tmp → `fsync` → `rename`, каталоги spool синхронізовано, потім **одна** транзакція SQLite (`synchronous=FULL`) публікує версію. Після коду 0 джерело можна змінювати чи видаляти. | Жодної копії на backend-і. Spool лежить на тому самому диску, що й каталог. | `capture.backup`, `catalog.Catalog` |
| запис копії (`replicas.state=CONFIRMED`) | Backend повернув підтвердження з `oid`, довжиною і SHA-256 **збережених** байтів, і всі три збіглися з об'єктом (`check_ack`). Для каталогу й вузла підтвердження йде після `fsync(file)+rename+fsync(dir)` (Windows: `FlushFileBuffers` + атомарне перейменування). | Факт надсилання запиту станом не є і ніде не записується. | `replicate._execute`, `backends.base.check_ack`, `fsutil.write_durable` |
| `protected` — захищена версія | **Кожен** блок і маніфест версії мають `CONFIRMED`-копії щонайменше в `min_copies` різних доменах відмов; каталоги на одному пристрої (`st_dev`) рахуються одним доменом. | Домен відмов вузла задає оператор; два розділи одного фізичного диска мають різні `st_dev` і не розпізнаються. | `replicate.protection`, `replicate.refresh_version`, `repo.domains` |
| `degraded` | Дані прийнято й відновлюються (зі spool або наявних копій), але політику не виконано і автоматичних спроб не лишилось. | Не захищено. | `replicate._apply` |

`policy_satisfied` у JSON дорівнює `true` **лише** в стані `PROTECTED`. `backup` без `--wait` повертає 0 після
локального приймання; `backup --wait` повертає 0 тільки для `protected`.

## 2. Які відмови витримує кожен стан

| Відмова | `accepted_local` / `replicating` | `protected` |
| :-- | :-- | :-- |
| аварія процесу CLI чи служби | так: зафіксована транзакція ціла, незавершене захоплення стає `FAILED`, сироти прибирає `repair`, завислі `RUNNING` повертаються після `lease_seconds` | так |
| втрата живлення | так **за умови** чесного `fsync` ОС і носія (не перевірено фізично) | так за тієї ж умови |
| недоступність вузла | так: дані в spool, черга чекає з backoff; після `max_attempts` — `DEGRADED`, `repair` повертає в чергу | так: лишаються копії в інших доменах |
| втрата або пошкодження однієї копії | — | `verify` виявляє, версія стає `DEGRADED`, `repair` копіює з цілої копії |
| втрата локального диска (каталог і spool) | **ні**: такі версії можуть бути втрачені | так: `recover` із будь-якого backend-а з підписаними службовими файлами |
| втрата всіх копій об'єкта | ні | ні: restore відмовляє з кодом 7, часткові файли не з'являються |

## 3. Що потрібно для restore

| Шлях | Потрібно |
| :-- | :-- |
| `log3-vault restore` | локальний каталог сховища, парольна фраза (`LOG3_VAULT_PASSPHRASE`), хоча б одна ціла копія кожного об'єкта версії (spool або backend) |
| `log3-vault recover` → `restore` | один backend із підписаним `repo-config.json`, покажчиками версій і об'єктами; парольна фраза |
| `log3_restore.py` (без інсталяції) | Python ≥ 3.11 з `cryptography` і `zstandard`; каталог backend-а або вузол; **або** фраза + `repo-config.json`, **або** файл `key export` + його фраза. Каталог, `config.json`, пакет log3 і ML не потрібні |

Маніфест — залежність декодування: без цілої копії маніфесту версію не відновити, тому маніфест реплікується
так само, як блоки, і входить у визначення `protected`. Ключі після ротації: усі попередні ключі даних
лишаються в keyring і в експорті, тож старі версії відновлюються новою фразою. ML-модель restore не потрібна і
не імпортується.

## 4. Переповнення й вичерпання повторів

- `queue_max_jobs`, `spool_max_bytes`, `min_free_bytes` перевіряються **до** стійкого приймання: відмова з кодом
  5 (`E_QUEUE_FULL`, `E_SPOOL_FULL`, `E_DISK_FULL`), нові файли невдалої спроби прибираються, прийняті версії й
  оригінали не видаляються, щоб звільнити місце.
- Повний вузол відповідає 507; це звичайна невдала спроба. `job_id = uuid5(repo_id, oid:backend)` однаковий у
  всіх повторах, вузол обліковує квоту за `oid`, тож загублена відповідь не породжує другої копії чи списання.
- Затримка `min(cap, base·2^(n−1))·U(0.5, 1.5)`; після `max_attempts` завдання `ATTENTION`, версія `DEGRADED`,
  `status`/`run` повертають 4, `health` — `attention_jobs` не пройдено. `repair` повертає такі завдання в чергу.

## 5. Ключі й службові файли

- Nonce AES-GCM випадковий (96 біт); монотонний лічильник об'єктів на ключ (`meta sealed:<key_id>`) і межа
  `crypto.max_objects_per_key` (типово 2^30 ≪ 2^32) з автоматичною ротацією перед backup.
- `repo-config.json` і покажчики версій на backend-ах підписані HMAC (ключ службових файлів виводиться з
  ключа ідентифікаторів); підпис прив'язаний до назви файла. `recover` відхиляє підміну політики й
  переставлені покажчики (тест `test_signed_meta_rejects_tampering_and_legacy_needs_flag`); непідписані файли
  сховищ до етапу 3 — лише з `--accept-legacy-meta`.

## 6. Матриця відмов

Кожен рядок — етап `matrix:<id>` модуля захисту; перевіряється (а) побайтова повнота restore для станів,
які система заявила, (б) коректність повторів, (в) відсутність помилкового `protected`.

| id | Відмова | Як моделюється | Що перевіряється |
| :-- | :-- | :-- | :-- |
| crash-after-accept | зупинка після приймання, до реплікації | `capture.after_publish` | повтор `--op-id` не створює другої версії; після `run` — `PROTECTED`, квоту вузла списано раз, restore побайтово |
| lost-response | запис завершився, відповідь загубилась | вузол `node_drop_response_once` | повторний PUT — дублікат, квоту не списано вдруге, restore побайтово |
| crash-block-manifest-catalog | аварія між блоком, маніфестом і каталогом | `capture.after_first_chunk`, `capture.before_publish`, `replicate.after_put_before_commit` | сироти й `CAPTURING` прибирає `repair`, жодна версія не `PROTECTED`; після аварії реплікації повтор ідемпотентний |
| node-outage | тривала недоступність вузла | процес вузла зупинено | `ATTENTION`/`DEGRADED`, код 4; restore під час відмови; після повернення `repair` → `PROTECTED` |
| disk-full | заповнення локального й віддаленого диска | `min_free_bytes`, `spool_max_bytes`, квота вузла | код 5 до приймання без файлів у spool; квота вузла не перевищена; після звільнення — `PROTECTED` |
| corruption | пошкодження копії й маніфесту | зміна байта, видалення об'єкта, пошкодження маніфесту | `verify` (код 7), `DEGRADED`, `repair`; маніфест із другої копії; без цілого маніфесту — відмова без часткових файлів |
| catalog-loss | втрата основного каталогу | каталог сховища перейменовано | `recover` із backend-а, `repair` визнає наявні копії, restore побайтово |
| restart-repair-gc | перезапуск при незавершеному repair/GC | `repair.after_requeue`, `gc.after_mark_deleted` | завдання repair у черзі після аварії; повторний gc дочищає; живі версії цілі |
| wrong-key | неправильний або недоступний ключ і токен | порожня/хибна фраза, хибний токен вузла | код 8 для backup/restore; `run`/`status` без фрази працюють; хибний токен → `DEGRADED`, не `protected` |
