# Огляд проєкту LOG3

## Що будуємо

Система зберігає максимум **цінних** подій журналу за обмеженого бюджету реплікації, відновлює критичні події після відмов вузлів і не розкриває зміст журналів тому, хто має доступ до копій. Три частини: агент журналу (класифікація, стиснення, пакування), планувальник реплікації (які події, у скількох копіях, на який вузол), відновлювач (перевірка, розшифрування, дедуплікація). Модель вузлів і відмов — готовий `replication.py` викладача; **змінювати його не можна**.

## Конвеєр і відповідальні

```
події → [1] класифікація (перцептрон)      — Artem
      → [2] стиснення (канонічний Гаффман) — Yaroslav (алгоритм), Гліб (упаковка в LOG3)
      → [3] вибір подій і копій (ДП)       — Yaroslav
      → [4] вузли й порядок (жадібні)      — Yaroslav
      → [5] шифрування AES-256-CTR + HMAC  — Гліб
      → вузли replication.py → відновлення — Гліб
[6] ГА налаштовує параметри — Artem · [7] модуль атаки — Artem · формат, метрика Q, звіт — Гліб
```

## Метрика

`Q = α·S + β·R + γ·T`, `α+β+γ = 1` (значення — у `materials/team_config.json`).

- `S = B_ref / (B_ref + B_stored)`, `B_ref = 16 × кількість записів`, `B_stored = 8 × global_used_bytes` (усі спроби запису, що спожили ресурс, включно з невдалими через стан BAD; відхилені до списання через бюджет не рахуються).
- `R` — частка критичних подій, відновлених після сценарію відмов.
- `T = t_ref / (t_ref + t)`, `t` — час повного прогону.
- Відновлювач упав або не відновив жодної критичної події → `Q = 0`.
- Офіційно Q рахують у середовищі викладача на п'яти прихованих seeds.
