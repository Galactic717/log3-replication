# Звіт: LOG3 — розумна захищена система пріоритетної реплікації журналів подій

> **Чернетка.** Структура взята з методички (Додаток В). Розділи зони FMT/SEC/INT (Гліб) заповнено. Розділи інших зон і числа офіційного середовища допишемо, коли будуть пакет викладача (`materials/`), перцептрон і ГА. Таблиці не переписуємо руками: їх генерує `python scripts/reproduce.py` у `results/tables/`.

## 1. Постановка задачі

Edge-вузли й сервери генерують журнал подій із 16-байтових записів. Сховище з трьох вузлів (A, B, C) має обмежену місткість і глобальний бюджет запису. Частина спроб запису втрачається (стан BAD), а невдала спроба теж витрачає ресурс. Треба вирішити, які події зберегти, у скількох копіях (0–3) і на яких вузлах, щоб після відмов відновити максимум критичних подій. Копії мають бути зашифровані так, щоб той, хто має доступ до вузлів, не бачив змісту журналу. Якість оцінюють метрикою `Q = α·S + β·R + γ·T`.

## 2. Архітектура

```
session -> [1] перцептрон (клас 0/1/2) -> v_i = priority(class) + critical_bonus·critical
        -> [2] таблиця Гаффмана вікна -> w_i = Σ довжин кодів 16 байтів
        -> [3] ДП r_i ∈ {0..3} під бюджет вікна W -> [4] жадібне розміщення по вузлах, batch ≤ max_batch_bytes
        -> [5] payload LOG3 -> AES-256-CTR -> HMAC-SHA256 -> store() на вузли (replication.py)
        -> репліки, що вижили -> приймання (HMAC до розшифрування) -> дедуплікація -> S, R, T, Q
[6] ГА налаштовує (window_records, no_compression_threshold, second_copy_factor) через pipeline.evaluate
[7] атака: ГА проти слабкого навчального шифру; tamper-тест через replica.as_receiver
```

## 3. Алгоритми і структури даних (зона Гліба)

### 3.1. Формат репліки LOG3

`HEADER(43) | CIPHERTEXT | HMAC(32)`. Заголовок: `"LOG3"`, version=1, replica_group_id (u16), batch_seq (u32), salt (16), nonce (12), ciphertext_len (u32), усе big-endian. Payload: record_count, flags, reserved, table_nsym, таблиця `(symbol, length)`, symbol_count, bitstream_len, bitstream, необов'язкова class_table. Головний інваріант: `symbol_count = 16 × record_count`.

Канонічний Гаффман: у потік кладуть лише довжини кодів. Приймач однаково відновлює коди алгоритмом `bl_count/next_code`, тож дерево передавати не треба (це економить місце й однозначно визначає коди). Для малих batch таблиця (2 B на символ) дорожча за виграш, тому payload переходить на `NO_COMPRESSION`, якщо стиснений варіант довший за `поріг × сирий`. Поріг — ген ГА. Точний розмір batch рахує одна функція `payload_size`: її використовують і планувальник, і `build_payload`, тож оцінка розміру дорівнює фактичному.

### 3.2. Захист

- `master = PBKDF2-HMAC-SHA256(password, salt, 100000, 64)`, `K_enc = master[0:32]`, `K_mac = master[32:64]`. Окремі ключі розділяють шифрування й автентифікацію: витік або злам одного не дає іншого. PBKDF2 виконується один раз на сеанс (кеш за `(password, salt)`), інакше T впаде в десятки разів.
- AES-256-CTR, блок лічильника `nonce(12) || uint32_BE(i)`, `i` від 1. Повтор nonce з тим самим ключем дає той самий keystream, і `C1 ⊕ C2 = P1 ⊕ P2`, тому nonce щоразу випадковий.
- Encrypt-then-MAC: HMAC рахується над заголовком і шифротекстом і перевіряється за сталий час **до** розшифрування. Змінений байт (зокрема в заголовку) або чужий пароль зупиняє приймання на `E_HMAC`, і парсер не бачить зловмисних даних.
- Порядок приймання (§5): `E_SHORT -> E_MAGIC -> E_LENGTH -> E_HMAC -> розшифрування -> E_PAYLOAD / E_CODE`. Назовні виходить лише `Log3Error`; це перевіряють fuzz-тести на тисячах випадкових змін.

### 3.3. Відновлення і метрика

Кожна репліка, що вижила, проходить повне приймання; зіпсовані відкидаються. Записи зливаються за точним 16-байтовим поданням (FORMAT_SPEC §1), тож копії однієї події не рахуються двічі, а різні події не склеюються. `R` — частка критичних подій, знайдених серед відновлених. `B_stored = 8 × global_used_bytes` включає невдалі спроби. `Q = 0`, якщо відновлювач упав або не відновив жодної критичної події.

### 3.4. Складність

| Операція | Час | Пам'ять |
| :-- | :-- | :-- |
| Гаффман: побудова | O(n + k log k), k ≤ 256 | O(k) |
| Гаффман: декодування | O(біт потоку) | O(k) |
| ДП на вікно | O(n·W·Rmax) | O(n·W) байтів для відновлення вибору |
| Жадібний рюкзак | O(n²·Rmax) | O(n) |
| Розміщення | O(n·|вузлів|·log|вузлів|) | O(n) |
| Відновлення | O(Σ розмірів реплік) | O(унікальних записів) |

## 4. Реалізація

Python 3.11, `numpy` (векторний рядок ДП), `cryptography` (AES), stdlib для PBKDF2/HMAC. Розподіл модулів — у `README.md`. Контракти між модулями — `docs/CONTRACTS.md`.

## 5. Тестування

`pytest -q`: юніт-тести кожного модуля, negative-тести (bad magic/version, обрізана репліка, зайвий байт, змінений HMAC/шифротекст/заголовок, невірний пароль, reserved ≠ 0, невідомі прапорці, Kraft ≠ 1, зайвий байт потоку, ненульовий padding, некоректний клас), вектор NIST SP 800-38A для AES-CTR, перебір для ДП, fuzz парсерів. Статус 12 кейсів C1 — у `results/c1.md`.

Попередні висновки (dev-середовище, перевірити на `replication.py`):

- Шифротекст не стискається: Гаффман і zlib після AES дають ≥ 100 % сирого розміру, а до шифрування Гаффман дає ≈ 54 %. Тому порядок «стиснути → зашифрувати» обов'язковий.
- Друга копія різко піднімає R у деградованому сценарії (max 1 копія: R ≈ 0.77; max 2: ≈ 0.96), але коштує бітів (S падає).
- В аварійному сценарії головне обмеження — глобальний бюджет: ДП бачить лише бюджет вікна, тож ранні вікна витрачають ресурс на 2–3 копії. Без стиснення R навіть вищий. Пропозиція: прив'язати W до залишку глобального бюджету (`docs/DECISIONS.md`).
- S низький (≈ 0.06), бо кожен batch несе таблицю Гаффмана всього вікна (до 512 B) і 75 B обгортки. Більше вікно амортизує ці накладні витрати; це ген ГА.
