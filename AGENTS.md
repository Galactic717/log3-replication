# AGENTS.md — інструкція для AI-агентів

Репозиторій командного проєкту «LOG3: пріоритетна реплікація журналів подій» (КНУ, 3 учасники).
Ти працюєш на **одного** учасника — того, хто тебе запустив. Код пишуть люди разом з агентами; людина відповідає за кожен рядок і захищатиме його усно, тому пояснюй, що і чому ти робиш.

## 1. Що прочитати перед роботою (у цьому порядку)

1. `docs/OVERVIEW.md` — що будуємо, хто за що відповідає, терміни.
2. `docs/CONTRACTS.md` — сигнатури та інваріанти між модулями.
3. `docs/tasks/<github-login>.md` — завдання твоєї людини. Логін: `gh api user --jq .login`.
4. Специфікації викладача в `materials/` (локально, **не в git**): `FORMAT_SPEC_P3.md`, `REPLICATION_SPEC.md`, `team_config.json`, `replication.py`, дані, `reference/`.

Якщо `materials/` порожня або чогось бракує — зупинись і скажи людині, що саме. Не вигадуй вміст специфікацій.

## 3. Жорсткі правила

- **Лише своя зона.** Редагуй тільки файли зі списку «Файли у твоїй власності» у завданні своєї людини. Потрібна функція з чужої зони, а її ще нема — бери заглушку з `docs/CONTRACTS.md` («Заглушки») і не реалізовуй її сам.
- **Контракти.** Сигнатури з `docs/CONTRACTS.md` не змінюй мовчки. Зміна — окремий PR у `dev` з апрувом голови та власника зачепленого модуля. Якщо контракт суперечить специфікації викладача — права специфікація; запиши розбіжність у `docs/DECISIONS.md`.
- **Автор коміту — людина.** Не чіпай `git config`, не підміняй ім'я/пошту. У кінець повідомлення коміту додай рядок `Co-Authored-By: <агент/модель> <noreply@anthropic.com>` (для не-Claude агентів — його назва).
- **Гілки й PR.** Працюй на гілці зони або `feat/<зона>-<задача>` від неї. Зміни — PR у `dev` (`dev` → `main` робить голова перед чекпоінтами). Не пушити напряму в `main`/`dev`, не робити force-push, не обходити хуки (`--no-verify`).
- **Не комітити:** `materials/`, `gen_project3.py`, `teacher/`, `holdout.csv`, `official_eval.json`, `.env`, ключі й паролі.
- **Тести першими.** `pytest -q` має бути зеленим до PR. Приймальні кейси називай `test_c1_<NN>_<назва>` (NN — номер із `docs/OVERVIEW.md`), додаткові — `test_d1_<NN>_<назва>`.
- **Детермінізм.** Усе випадкове приймає `seed`; результати експериментів відтворюються однією командою.
- **Без зашитих констант.** Параметри моделі й умови (бюджет, вікно, пріоритети класів, надійність вузлів, кількість класів і вузлів) беруться з `Config` (`materials/team_config.json`). На захисті умову змінюють, і це має зводитись до правки конфігу.
- **Результати.** Таблиці, графіки й журнали експериментів лежать у `results/` (перелік — у `docs/OVERVIEW.md`) і створюються скриптами, не руками.
- **Стек.** Python ≥ 3.11, stdlib + `numpy`. Перцептрон — тільки власний код (прямий прохід, backprop, SGD/Adam): `torch`, `tensorflow`, `sklearn`-моделі заборонені. Решта залежностей — через `requirements.txt` із відома голови.
- **Не вгадуй.** Специфікація мовчить або двозначна — запитай людину і запиши рішення в `docs/DECISIONS.md` (дата, питання, рішення, хто вирішив).

## 4. Звітність про використання ШІ

Після кожної сесії допиши рядок у `META-USAGE.md`: дата, учасник, агент/модель, що просили, що прийнято, що відхилено, чи людина зрозуміла й перевірила код. На захисті будуть питання за кодом і «мікрозміни умови» — людина має вміти змінити свій код сама, тож не залишай «магії» без пояснення в PR.

## 5. Як вважати роботу завершеною

- Усі пункти «Що має працювати» зі свого завдання відмічені `- [x]`.
- `pytest -q` зелений, свої `test_c1_*` проходять.
- PR описує: що зроблено, які кейси C1/D1 закриває, як запустити, що лишилось.
